# v0.5.3 Release Notes

Release notes for the `metz-scan` and `rubocop-metz` `v0.5.3` release.

This is a republish of the `v0.5.2` changes at `0.5.3` with no source or
behavior change. The `rubocop-metz 0.5.2` gem published to rubygems.org was
corrupt: it was built by running `gem build rubocop-metz/rubocop-metz.gemspec`
from the repo root instead of from `rubocop-metz/`, so the gemspec's
CWD-relative `Dir.glob` packaged the wrapper's `lib/metz_scan` files instead
of `rubocop-metz`'s own `lib/`. `require "rubocop-metz"` fails for anyone who
installed that gem. rubygems.org does not allow overwriting a published
version, so `0.5.2` is being yanked and superseded by a clean `0.5.3`.

## Highlights

- No behavior or source change from `v0.5.2`. See
  [`docs/releases/v0.5.2.md`](v0.5.2.md) for the full set of fixes carried
  forward (#37 default-scan exclude honoring, the absent-target-extension
  crash fix, `TargetRubyVersion` preservation, the
  `ControllersTooManyDirectCollaborators` over-count fix, and the
  `inherit_gem`-absent warning).
- Root-cause fix: both `rubocop-metz/rubocop-metz.gemspec` and
  `metz-scan.gemspec` now resolve their file lists relative to the gemspec's
  own directory (`__dir__`), not the process's current working directory, so
  `gem build <path>` produces correct gem contents regardless of the
  directory `gem build` is invoked from. This is the fix that prevents the
  `0.5.2` corruption from recurring.

## Release Readiness

- Both gems now report `0.5.3`.
- No behavior-policy or threshold change from `0.5.2`.
- Gemspec hardening verified: building both gems from the repo root now
  produces file lists byte-identical to a correct (`cd`-first) build;
  `rubocop-metz`'s gem contains only `rubocop-metz`'s own files and
  `metz-scan`'s gem contains only `metz-scan`'s own files.
