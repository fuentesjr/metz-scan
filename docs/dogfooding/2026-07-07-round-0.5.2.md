# Dogfooding round: HEAD 0.5.2, 2026-07-07

rubygems.org exit criterion 2, rerun after `v0.5.1`. This round was run against
the **HEAD build (0.5.2)** rather than a published gem — a deliberate deviation
from the `dogfood-round` skill's "released gems" rule. Rationale: scan
*findings* are byte-identical whether run from HEAD or an installed gem of the
same code, so HEAD gives the full findings-quality signal; packaging/install
fidelity is a separate concern that belongs with the rubygems.org release
candidate (exit criterion 3), not this round. The reason the prepared `0.5.2`
release was *not* published first is recorded in `PROJECT_TRACKER.md` (a
throwaway GitHub Packages publish adds ceremony without changing findings).

Invocation (from each target root, target checked out **outside** the metz-scan
repo tree so RuboCop config resolution does not walk up into the repo):
`BUNDLE_GEMFILE=<repo>/Gemfile bundle exec metz-scan scan app lib`
(default mode; `--all-cops` and `--project-analyzers` as second reads).

**Verdict: NOT PASSED.** Four headline-UX-class defects, three of them
(crash + misattributed error) a regression introduced by the `#33`/`#37` fix
line and already shipped in the published `v0.5.1`.

## Headline-UX defects

### 1. Default-mode crash (exit 2) on targets that reference external RuboCop gems — regression from #33/#37

Any target whose `.rubocop.yml` uses `plugins:`, `require:`, or `inherit_gem:`
for a gem not present in the bundle metz-scan runs in crashes hard in **every**
mode. Confirmed on redmine (`rubocop-performance`, `rubocop-rails`), maybe
(`inherit_gem: rubocop-rails-omakase` — the Rails 8 `rails new` default), and
rubygems.org (five plugins). `rubocop-rails`/`-performance`/omakase are close to
the default case for real Rails apps.

Repro (clean target checkout, any bundle lacking the target's plugins):
```
$ BUNDLE_GEMFILE=<repo>/Gemfile bundle exec metz-scan scan app lib
metz-scan scan: RuboCop failed: could not load rubocop-metz: cannot load such file -- rubocop-performance
$ echo $?
2
```

Root cause, verified in source and git history: default mode consults the
target's config to honor its `Exclude` scope —
`TargetFileDiscovery.for_project_config` (`runner.rb:180`) and
`ProjectCopScope.honor` (`runner.rb:145-166`) both build a plain
`RuboCop::ConfigStore` (no `force_default_config!`) and call `for_dir`/`for_file`
on the target directory. RuboCop's config loader eagerly `require`s every gem
under the target's `plugins:`/`require:`/`inherit_gem:` *before*
`--force-default-config` ever takes effect. `git log -S ConfigStore --
lib/metz_scan/commands/scan/runner.rb` pins the introduction to `d041d51` (#33)
and `847c478` (#37). **Pre-#33 default mode never read the target config, so it
never loaded those gems and never crashed** — this is a regression, and it is
already in published `v0.5.1`.

Design tension the fix must resolve: default mode *forces default config and
discards the target's cop config*, yet now requires the target's RuboCop plugin
gems to be installed just to read `Exclude` scope. The exclude *feature* is
correct (verified in defect-free targets below); the plugin-loading side effect
is the bug. A fix must resolve `Exclude` scope without triggering plugin loading
(e.g. force default config on the discovery/scope store too, read
`AllCops: Exclude` directly, or catch the plugin `LoadError` and degrade rather
than crash — degrading silently would reintroduce #33, so the tradeoff needs a
decision).

### 2. Crash error message blames the wrong component; `--all-cops` leaks a raw backtrace

`Runner#raise_load_error` (`runner.rb:40-42`) hardcodes
`"could not load rubocop-metz: #{err.message}"` for **any** `LoadError` reaching
`with_errors` — so the defect-1 crash (a missing *target* plugin) is reported as
a rubocop-metz load failure. rubocop-metz loaded fine; the message points the
user at the wrong culprit. In `--all-cops` mode the same failure takes the
generic `StandardError` branch and leaks a raw backtrace fragment, because
`concise_message`'s stack-trace filter (`runner.rb:107-109`, regex
`/\.rb:\d+:in /`) does not match the extension-less entry point
`bin/metz-scan:10:in`. Independent of the defect-1 scope debate, hardcoding
"rubocop-metz" for every `LoadError` is a code-level bug.

### 3. Default mode loses the target's `TargetRubyVersion`, producing false `Lint/Syntax`

`--force-default-config` discards the target's declared `TargetRubyVersion`;
RuboCop falls back to its floor (Ruby 2.7) parser, which flags legitimate
Ruby 3.1+ syntax as syntax errors. `Lint/Syntax` always runs regardless of
`--only Metz`, so these false positives pollute the "Metz-only" default output.
On redmine this produced **194 bogus `Lint/Syntax` offenses on 50+ real,
non-excluded production files** (e.g. `app/helpers/application_helper.rb:661`,
`def project_tree(projects, options={}, &)` — anonymous block forwarding).

Isolated repro (no target checkout needed):
```
# .rubocop.yml: AllCops: { TargetRubyVersion: 3.2 }
# sample.rb:
module Sample
  def wrapper(a, b = {}, &)
    other(a, b, &)
  end
end

$ metz-scan scan .            # default mode -> Lint/Syntax "unexpected token tRPAREN" (Ruby 2.7 parser)
$ metz-scan scan . --all-cops # honors TargetRubyVersion 3.2 -> no Lint/Syntax
```

Not a #33/#37 regression — this has existed since default mode shipped in
`0.5.0`; it is the same *symptom class* as the original #33 template-file noise,
now surfacing on live application code and by a different mechanism.

### 4. `Metz/ControllersTooManyDirectCollaborators` over-counts collaborators

The cop counts constants that are not domain collaborators, inflating the count
and the message — the same defect class as #34 (whose fix excluded exception
constants at `rescue` sites but did not carry to this sibling cop). Two verified
facets across two codebases:

- **Raise-site exception classes.** `rescue_exception_class?`
  (`controllers_too_many_direct_collaborators.rb:136-141`) only excludes a
  constant with a `:resbody` ancestor — i.e. at the `rescue X` site. The same
  class at a `raise X` site inside the body is counted. lobsters
  `login_controller.rb`: `login` is reported as reaching **8 direct
  collaborators (User, LoginFailedError, LoginWipedError, LoginPasswordTooLong,
  LoginBannedError, LoginDeactivatedError, BCrypt::Engine::DEFAULT_COST,
  ModNote)** — 5 are file-local `StandardError` subclasses raised and rescued in
  that same method. Honest external count: 3. huginn adds the framework variant
  (`ActionController::RoutingError`, `ActiveRecord::RecordNotFound` at raise
  sites).
- **Framework query/SQL helpers.** No framework allowlist (unlike the sibling
  `DemeterTrainWreck`, which excludes `Rails, Arel, Time, Date, DateTime` via
  `AllowedReceivers`). huginn `jobs_controller.rb`: an ordinary
  `Delayed::Job.order(Arel.sql("..."))` one-liner is reported as **2 direct
  collaborators (Delayed::Job, Arel); Max is 1**.

## Findings-quality notes (queue candidates, not blocking)

- **`Metz/MethodsTooLong` (Max: 5) dominates 80–90% of default output** on every
  target (333/435 lobsters, 558/622 huginn, 567/697 maybe, 818/1261 redmine,
  512/636 rubygems.org). A large share are 6–8 line methods (single chained AR
  queries, `case`-mapping DSL blocks in ViewComponents/Avo/OpenSearch) that a
  reviewer would triage away. The strict default is deliberate, but it buries
  the sharper cops (`DemeterTrainWreck`, `ControllersTooManyDirectCollaborators`)
  and there is no signal in the output that this cop is unusually strict.
- **No grand-total / per-cop rollup line in text output.** The reader must tally
  bullets by hand or switch to JSON to learn one cop is 90% of the report.
  `text_renderer.rb` emits a header only for the `MetzProject/*` block.
- **No legacy-adoption path** (todo-style baseline or top-offender ranking) for a
  first scan that emits hundreds of offenses.
- **`MetzProject/RepeatedBranching` false positives from coincidental subject
  names.** On redmine ~36% (4/11) were misleading: unrelated methods matched
  only because they share a generic local-variable name (`arg`, `value`, `line`)
  plus a generic `is_a?`/`start_with?` dispatch idiom. The `k (state branch
  subject)` label on lobsters names the loop variable, not the decision domain.
- **`RootKind` base-class allowlist has no `*Component` entry.** On maybe,
  `DesignSystemComponent` (14 descendants) is triaged at higher alarm than
  `ApplicationRecord` (66) purely because "Component" is not in the
  Controller/Job/Mailer/Record allowlist.
- **`MetzProject/SubclassOverridePressure`** suggests "consider naming the hook
  protocol" even when the base already declares it via `raise NotImplementedError`.
- **"status: validated" label** is shown in `--project-analyzers` for analyzers
  that can never reach default output (no `DEFAULT_OUTPUT_ELIGIBLE`), reading as
  if they should be visible by default.

## Findings that earned their space

The analyzers' numeric accuracy was high across all targets (huginn: 13/13
project-analyzer counts exact; rubygems.org: 4/4; maybe: 18 checked, all exact).
Concrete wins: lobsters `RepeatedBranching` on the copy-pasted `as_json` key
loop and `RepeatedQueryCriteria` on `SavedStory.where(user_id:, story_id:)`
across 3 files; huginn `RepeatedBranching` on `OpenaiConcern` re-implementing a
faraday-adapter `case` its own included `WebRequestConcern` already provides;
maybe `ImplicitContextPressure` on `Current.family` (45 files, count exact) and
`RepeatedBranching` on duplicated `safe_per_page_param`; rubygems.org
`RepeatedBranching` on three copy-pasted `case` blocks (`range`, `value`,
`api_key_owner`). The `#33`/`#37` exclude-honoring **feature** works: verified on
rubygems.org (`dynamic_errors_helper.rb` excluded; Metz offense sets identical
default vs `--all-cops`, 632/632) and redmine (no offenses under
`lib/generators/**/templates/*`).

## Methodology note (harness, not a metz-scan bug)

Cloning targets under a path containing `/tmp/` collides with targets that use
**unanchored raw-regexp** excludes (rubygems.org's
`!ruby/regexp /(vendor|bundle|bin|...|tmp|server)($|\/.*)/` matches `tmp` as a
substring of the absolute path), yielding a **false-clean 0-file scan**. Glob
excludes (redmine's `**/tmp/**/*`) are base-anchored to the config dir and are
not affected. The `dogfood-round` skill should clone targets outside any
`tmp`-containing path and sanity-check `target_file_count > 0`.
